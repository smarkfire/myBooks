## 开篇故事：两个程序员的同一个Bug

2025年秋天，字节跳动TRAE团队做了一个经典实验。

他们找了一个中等复杂度的Bug——一个跨组件的状态同步问题。然后把Bug分别交给两个小组：

**A组（传统方式）**：直接把Bug描述丢给AI，说“帮我修一下”。
**B组（上下文工程方式）**：在提交Bug之前，先整理了相关代码文件、组件依赖关系图、最近5次相关提交记录、以及一个复现Bug的最小测试用例。

结果：
- A组：AI修复了Bug，但引入了3个新Bug。修复成功率：59%。
- B组：AI一次修复成功，没有引入新Bug。修复成功率：**100%**。

同一个Bug，同一个AI模型。唯一的区别是：**B组给了AI“正确的上下文”。**

这不是一个关于“AI有多厉害”的故事。这是一个关于“**你给AI什么东西，决定了AI给你什么东西**”的故事。

## 8.1 上下文工程深度解析

### 什么是上下文工程？

在AI开发中，我们花了太多时间研究“用什么模型”、“调什么参数”、“写什么Prompt”。但有一个被严重低估的变量——

**上下文（Context）——你给AI看了什么信息。**

上下文工程（Context Engineering）就是在问一个问题：**为了让AI做出最好的决策，它需要看到什么？不需要看到什么？**

**浅读区（大白话）**

上下文工程就像给医生看病历。你给医生看“咳嗽三天”和给医生看“咳嗽三天+体温38.5度+血常规报告+胸片”，医生做出的诊断质量天差地别。

AI也一样。你扔给它一个模糊的问题，它只能给你一个模糊的答案。你给它结构化的、精选的、高质量的上下文，它就能给你精准的、可靠的、高质量的输出。

**深读区（技术细节）**

> 上下文工程包括四个核心子领域：
>
> 1. **上下文选择**：从海量信息中挑出最相关的部分。关键挑战是“相关性判断”——什么信息对当前任务真正有用？
>
> 2. **上下文排序**：信息按什么顺序呈现？研究表明，重要信息放在开头和结尾效果最好，中间部分容易被“遗忘”（Lost-in-the-Middle效应）。
>
> 3. **上下文压缩**：如何在有限Token窗口内塞入最多有效信息？方法包括摘要、去重、结构化编码。
>
> 4. **上下文隔离**：如何防止不相干的信息“污染”当前任务？这和第5章的“注意力治理”一脉相承。
>
> 字节TRAE团队的实验数据表明，上下文质量对输出质量的影响系数约为0.78，而模型选择的影响系数约为0.35。这意味着**上下文质量的影响力是模型选择的2.2倍**。

### 四大上下文工程实践策略

**策略一：渐进式索引（Progressive Indexing）**

不要一次性把所有代码文件都塞给AI。而是建立一个“索引”——先让AI看到目录结构、文件清单、接口定义，然后根据需要逐步深入。

```
第一层：项目结构（1000 token）
第二层：相关文件列表（2000 token）  
第三层：关键文件内容（5000 token）
第四层：完整实现细节（按需加载）
```

这就像你去图书馆查资料——你不会把整座图书馆的书都搬回家，而是先查目录，再找书架，再翻具体章节。

**策略二：Code First原则**

2026年最好的AI实践之一：**用代码代替自然语言描述。**

与其说“当用户点击按钮时，需要验证表单然后提交到服务器”，不如直接给AI看：

```typescript
// 这就是上下文——比自然语言描述精确100倍
async function handleSubmit(form: FormData): Promise<Result> {
  const errors = validateForm(form);
  if (errors.length > 0) return { success: false, errors };
  return await api.submitForm(form);
}
```

代码不会产生歧义。自然语言会。**代码是AI理解你的意图的最佳语言。**

**策略三：Skills技能包**

这和第7章的Harness Engineering一致。把常用的操作封装成Skill，AI可以直接调用，而不需要每次都重新“理解”。

**策略四：Session-Learning（会话学习）**

让AI在完成任务后，自动总结这次会话中学到的东西，存储为一个“学习卡片”。下次类似任务，直接把学习卡片作为上下文的一部分注入。

```python
# Session-Learning的简单实现
def save_learning(session_id: str, task: str, lesson: str):
    """保存这次会话的教训"""
    card = {
        "task": task,
        "lesson": lesson,
        "timestamp": datetime.now().isoformat(),
        "tags": extract_keywords(task)  # 自动提取关键词作为标签
    }
    # 存储到向量数据库，下次可以语义检索
    vector_store.add(card)

# 下次任务开始时
def load_learnings(task: str, top_k=3):
    """加载与当前任务最相关的历史教训"""
    return vector_store.search(task, k=top_k)
```

## 8.2 Vibe Coding方法论

### 什么是Vibe Coding？

Vibe Coding是2025年由Andrej Karpathy（前OpenAI联合创始人、前Tesla AI总监）提出的概念。它描述了一种全新的编程范式：

**你不是在“写代码”，你是在“描述你想要什么”，然后AI帮你实现。**

但Vibe Coding不是“把一切都交给AI”。它的核心原则是：

> **"AI Does, Human Owns.“**
> AI负责执行，人负责决策和负责。

**浅读区（大白话）**

Vibe Coding就像你请了一个非常能干的助手。你告诉助手”帮我整理一下这个季度的销售数据，做成图表“，助手去执行，然后你检查结果。如果图表颜色不好看，你告诉助手”换成蓝色系“；如果数据有误，你指出问题让助手修正。

你不需要知道Excel怎么操作、图表怎么画——你只需要知道”什么样的是好的“。这就是Vibe Coding的精髓：**人定义”好“，AI实现”好“。**

### 七阶段责任矩阵

Vibe Coding把一个项目分为七个阶段。每个阶段，AI做什么、人审什么、人负责什么，界限分明。

| 阶段 | AI做什么 | 人审什么 | 人负责什么 |
|------|---------|---------|-----------|
| **Plan（规划）** | 基于需求生成技术方案和架构设计 | 方案是否合理、技术选型是否正确 | 最终决策——走哪条路 |
| **Design（设计）** | 生成UI设计稿、API设计、数据模型 | 设计是否符合业务需求、用户体验 | 设计决策——做成什么样 |
| **Build（构建）** | 生成代码，实现功能 | 代码逻辑是否正确、是否符合规范 | 代码质量——能不能用 |
| **Test（测试）** | 生成测试用例、执行测试 | 测试覆盖是否全面、边界场景是否考虑 | 质量标准——够不够好 |
| **Review（审查）** | 生成代码审查意见 | 审查意见是否合理、是否有遗漏 | 合并决策——放不放行 |
| **Document（文档）** | 生成API文档、使用说明 | 文档是否准确、是否易懂 | 最终文档——对不对 |
| **Deploy（部署）** | 生成部署配置、CI/CD脚本 | 部署方案是否安全、是否完整 | 发布决策——上不上线 |

**关键洞察：** 每一阶段都是”AI生成，人审核，人负责“。AI是”第一稿写手“，人是”主编“。AI永远不会为最终结果负责——**负责的那个人永远是你。**

### Vibe Coding的两个陷阱

**陷阱一：”看起来能跑“不等于”真的能跑“**

AI生成的代码通过了编译，不代表它没有逻辑错误。一个常见的场景：AI生成的代码在”正常情况“下完美运行，但在”用户输入了空字符串“时崩溃。

**对策：** 永远不要信任AI生成的代码。测试、测试、再测试。

**陷阱二：上下文丢失**

当你和AI合作了50轮对话后，AI的”记忆“可能已经混乱。它可能忘记了你之前说的”不要用Redux“，或者”API地址是staging环境“。

**对策：** 定期”重置上下文“——把关键约束重新注入。用CLAUDE.md或README.md作为”持久化上下文“文件。

### 深读区：Vibe Coding的效率数据

> 根据2026年初GitHub的开发者调查：
> - 使用Vibe Coding的开发者，平均编码速度提升2.7倍
> - 但Bug率也提升了约1.4倍（因为”看起来能跑“的代码变多了）
> - 最终净效率提升约为1.9倍（修复Bug的时间抵消了部分速度提升）
> - 最关键的数据：**经验越丰富的开发者，从Vibe Coding中获益越多**（因为他们能更快发现AI生成的Bug）
>
> 这印证了一个反直觉的结论：**Vibe Coding最受益的不是新手，而是有经验的开发者。** 新手容易被AI生成的代码”骗"过去，而有经验的开发者能快速识别问题并精准指导AI修正。

## 8.3 Spec Coding——把需求写清楚

### 为什么Spec是命门？

Vibe Coding最大的痛点是什么？不是AI不够聪明，而是**你描述不清楚你要什么**。

你试过让AI帮你做一件事，然后它做了，但完全不是你想要的吗？绝大多数情况下，问题不在AI，在于你的需求描述。

**Spec Coding就是：在让AI写代码之前，先让AI帮你把需求写清楚。**

### 五步标准化流程

**第一步：填痛点表**

```
痛点表（Pain Point Sheet）
─────────────────────────────
1. 当前状况：现在是怎么做的？哪里不爽？
2. 期望状态：理想情况下，应该是什么样？
3. 使用场景：谁来用？在什么情况下用？频率如何？
4. 约束条件：有什么限制？（技术栈、预算、时间、合规）
5. 成功标准：怎么判断"做好了"？
```

**第二步：Plan Mode追问**

把痛点表给AI，然后进入"Plan Mode"——AI在这个模式下只问问题，不写代码。

```
"你现在是Plan Mode。请基于我的痛点表，列出你需要澄清的问题。
不要写代码，不要设计方案，只提问。"
```

这一步的价值在于：**AI会问出你没想到的问题。** 比如你描述了一个“用户注册功能”，AI可能会问：“注册需要手机验证吗？密码强度要求是什么？注册成功后跳转到哪里？”——这些问题你可能完全没想过。

**第三步：输出spec.md**

AI把澄清后的需求整理成一份结构化的Spec文档。

```markdown
# Spec: 用户注册功能

## 概述
用户可以通过邮箱或手机号注册账户。

## 功能需求
### FR-1: 注册表单
- 必填字段：邮箱/手机号、密码、昵称
- 密码要求：至少8位，包含数字和字母
- 邮箱格式验证

### FR-2: 验证码
- 发送6位数字验证码到邮箱/手机
- 验证码有效期5分钟
- 每天最多发送5次

### FR-3: 注册成功
- 自动登录
- 跳转到个人资料完善页
- 发送欢迎邮件

## 非功能需求
- 注册接口响应时间 < 500ms
- 支持1000并发注册
- 密码加密存储（bcrypt）

## 验收标准
- [ ] 用有效邮箱能成功注册
- [ ] 用无效邮箱被正确拦截
- [ ] 重复邮箱被正确提示
- [ ] 验证码过期后不能使用
```

**第四步：互审（Cross-Review）**

把Spec给另一个AI模型看，让它挑刺。

```
"请以批判性思维审查这份Spec。找出所有模糊之处、矛盾之处、遗漏之处。"
```

为什么用另一个模型？因为同一个模型很难发现自己的“盲区”。这就像你很难发现自己文章中所有的错别字——你需要另一个人帮你读。

**第五步：拆任务**

把Spec拆成一系列可独立执行的小任务，每个任务对应一个AI交互。

```
任务拆分原则：
- 一个任务只做一件事
- 每个任务有明确的输入和输出
- 任务之间有清晰的依赖关系
- 每个任务都可以独立验证
```

### Spec模板

这是一个可以直接复制使用的Spec模板：

```markdown
# [项目名称] Spec

## 元信息
- 创建日期：YYYY-MM-DD
- 版本：0.1
- 状态：草稿 / 评审中 / 已确认

## 一句话描述
[用一句话说清楚这个项目是要做什么]

## 用户故事
- 作为[角色]，我想要[功能]，以便[价值]

## 功能需求
### F-1: [功能名]
- 描述：...
- 输入：...
- 输出：...
- 异常处理：...

## 非功能需求
- 性能：...
- 安全：...
- 兼容性：...

## 技术约束
- 必须使用：...
- 不能使用：...

## 验收标准
- [ ] 标准1
- [ ] 标准2

## 开放问题
- [ ] 待澄清的问题1
```

## 8.4 测试驱动开发——AI时代的TDD

### 测试不是防Bug，而是“重构的勇气”

在AI辅助开发时代，测试的意义发生了根本性转变。

传统观念：测试是为了防止Bug。
新观念：**测试是为了让你敢于重构。**

当AI帮你生成了代码，你看着那堆“半生不熟”的逻辑，想改又不敢改——因为你不知道改了会不会出问题。但如果有一套完善的测试，你就能放心大胆地重构。**测试是安全网，让你敢于在AI生成的代码上“动手术”。**

**浅读区（大白话）**

测试就像你开车时的安全带。不是为了让你“故意撞车”，而是让你“敢于上路”。有了安全带，你才敢开快车、走远路。

**深读区（技术细节）**

> 在AI辅助开发中，测试的角色从“质量验证”演变为“契约定义”：
>
> - 测试定义了函数/模块的预期行为
> - 当AI修改代码时，测试是“AI没有破坏原有功能”的证明
> - 测试集是AI理解项目行为的“可执行文档”

### 简化TDD五步循环

传统TDD（测试驱动开发）的红-绿-重构循环在AI时代变得更高效：

```
Step 1: 写测试（定义期望）
Step 2: 让AI生成代码（实现功能）
Step 3: 跑测试（验证）
Step 4: 如果失败，把错误信息给AI（修正）
Step 5: 重构（优化代码，测试保底）
```

```python
# ============================================
# AI时代的TDD示例
# ============================================

# Step 1: 你先写测试——定义"什么样算对"
def test_parse_date():
    """测试日期解析函数"""
    assert parse_date("2024-01-15") == datetime(2024, 1, 15)
    assert parse_date("2024/01/15") == datetime(2024, 1, 15)
    assert parse_date("15-01-2024") == datetime(2024, 1, 15)
    assert parse_date("invalid") is None
    assert parse_date("") is None

# Step 2: 把测试给AI，让AI生成代码
# "请实现 parse_date 函数，让它通过以下测试：...（粘贴测试代码）"

# Step 3: 跑测试
# python -m pytest test_date.py

# Step 4: 如果失败，把完整错误信息给AI
# "运行测试报错：AssertionError at line 5... 请修复"

# Step 5: 测试通过后，你可以放心重构
# AI生成的代码无论多"丑"，只要测试全过，你就能安全地清理和优化
```

### 双模型互审：让AI们互相“找茬”

这是2026年最强大的质量保障实践之一。

```
工作流程：
1. 用Claude生成代码
2. 用Codex审查Claude的代码
3. 用Claude审查Codex的审查意见
4. 人做最终仲裁
```

为什么有效？因为不同模型的“盲区”不同。Claude看不到的Bug，Codex可能一眼看出；Codex忽略的安全问题，Claude可能特别敏感。

### Superpowers纪律系统

这个方法论来自一个被称为"Superpowers"的开源项目。核心思想是：**在AI生成代码之前，先定义好纪律（Disciplines），让AI在生成代码时自动遵守。**

```markdown
# Disciplines（纪律）示例
# 放在每个AI对话的开头

## 纪律1：无测试不代码
- 任何新函数必须先有测试
- 测试必须先于实现

## 纪律2：单一职责
- 一个函数只做一件事
- 超过50行的函数必须拆分

## 纪律3：类型优先
- 所有函数必须有类型注解
- 不使用Any类型

## 纪律4：错误处理
- 所有外部调用必须有try-catch
- 错误信息必须包含足够的上下文

## 纪律5：不可变优先

- 优先使用const/readonly
- 避免直接修改传入的参数
```

把这段纪律粘贴到每个新AI对话的开头，AI就会自觉遵守。**纪律不是限制AI，而是给AI一个“好代码的标准”。**

## 8.5 个人Agent养成——15天从0到日常使用

这一节是本书的“毕业设计”——把你的知识转化为一个真正属于你自己的、每天使用的AI Agent。

### 为什么是15天？

不是1天，因为Agent需要“磨合”——你需要时间来发现它的问题、调整它的行为。
不是30天，因为30天太长，中间容易放弃。
**15天是最佳节奏——足够长让系统稳定，足够短让你保持动力。**

### Day 1-3：选基座，建"骨架"

**Day 1：创建你的第一个Nanobot（约1-2小时）**

**你要做什么：** 在电脑上新建一个文件夹，创建一个`nanobot.py`文件，把下面的代码复制进去，然后运行它。

**需要准备：**
- 安装Python 3.10+（如果还没装，去python.org下载安装）
- 注册一个OpenAI账号并获取API密钥（或者用DeepSeek/通义千问的API密钥，国内更方便）
- 在终端运行：`pip install langchain-openai python-dotenv`

> **【配图建议】**：此处建议配一张终端截图，展示`pip install`成功后的界面。

```python
# nanobot.py —— 你的Agent的"受精卵"
# 功能：收到消息 -> 调用LLM -> 返回回复

from langchain_openai import ChatOpenAI

class NanoBot:
    def __init__(self):
        self.llm = ChatOpenAI(model="gpt-4o-mini")
        self.system_prompt = "你是一个有用的助手。"
    
    def chat(self, message: str) -> str:
        response = self.llm.invoke([
            ("system", self.system_prompt),
            ("human", message)
        ])
        return response.content

# 测试
bot = NanoBot()
print(bot.chat("你好，介绍一下你自己"))
```

**验收标准：** 运行`python nanobot.py`后，终端能打印出AI的回复。如果报错了，检查API密钥是否正确配置。

### Day 4-7：跑通消息通道

**Day 4：让Agent能"记住"对话（约1.5小时）**

**你要做什么：** 给Agent添加对话记忆能力。把下面的代码整合到你的`nanobot.py`中（不是替换，而是把`memory`和`_build_context`方法加进去）。

**核心概念：** `memory`是一个列表，存储每次对话的历史。每次调用LLM时，把历史对话也一起发过去，AI就能"记得"之前说过什么。

```python
# 加入记忆后的Agent（核心改动）
class NanoBot:
    def __init__(self):
        self.llm = ChatOpenAI(model="gpt-4o-mini")
        self.memory = []  # 简单的对话记忆
        self.user_profile = {}  # 用户画像——长期记忆
    
    def _build_context(self, message):
        # 构建包含历史对话的上下文
        context = [("system", self.system_prompt)]
        for m in self.memory[-10:]:  # 只保留最近10轮对话
            context.append(m)
        context.append(("human", message))
        return context
    
    def chat(self, message: str) -> str:
        context = self._build_context(message)
        response = self.llm.invoke(context)
        
        self.memory.append(("human", message))
        self.memory.append(("assistant", response.content))
        
        if len(self.memory) > 20:
            self.memory = self.memory[-20:]
        
        return response.content
```

**验收标准：** 连续问Agent三个相关问题，看它能不能在第三个问题中引用第一个问题的信息。

## 深读区：技术进阶

### CLAUDE.md最佳实践

> CLAUDE.md是Claude Code中的一个特殊文件，它作为“持久化上下文”在每个对话开始时自动加载。2026年，这个模式已经被多个AI编程工具采用。
>
> **最佳实践：**
>
> ```markdown
> # CLAUDE.md
> 
> ## 项目概述
> 这是一个[项目类型]，用于[目的]。
> 
> ## 技术栈
> - 前端：React 19 + TypeScript
> - 后端：FastAPI + Python 3.12
> - 数据库：PostgreSQL
> 
> ## 代码规范
> - 使用函数式组件，不用class组件
> - 所有API调用必须放在services/目录下
> - 错误处理：统一使用Result<T, E>类型
> 
> ## 不要做的事
> - 不要使用Redux（我们用Zustand）
> - 不要引入新的依赖不加讨论
> - 不要修改.env.example的内容
> 
> ## 当前已知问题
> - 登录页在Safari下有样式问题（暂不处理）
> - API限流逻辑待优化
> ```
>
> **关键原则：**
> 1. CLAUDE.md应该短小精悍（不超过200行）
> 2. 每周更新一次，删除过时信息
> 3. “不要做的事”比“要做的事”更重要

### Claude Code + Codex配置优化

> 2026年的双模型工作流最佳实践：
>
> - **Claude Code**：负责代码生成、重构、复杂推理。适合有大量上下文的任务。
> - **Codex（OpenAI）**：负责代码审查、测试生成、快速修复。适合快速、小范围的任务。
>
> 配置建议：
> - Claude Code设置`max_context_tokens=100000`，充分利用其长上下文优势
> - Codex设置`temperature=0.1`，确保审查的一致性
> - 两者都配置`.cursorrules`或`.aide-rules`来统一代码风格

### MCP Server开发

> 2026年，MCP（Model Context Protocol）已经成为Agent工具开发的标准。开发一个MCP Server可以让你的工具被任何支持MCP的Agent使用。
>
> MCP Server本质上是一个暴露了标准接口的HTTP服务，有三个核心端点：
> - `tools/list`：列出可用的工具
> - `tools/call`：调用指定工具
> - `resources/read`：读取资源（如文件、数据库记录）
>
> 开发流程：定义工具Schema -> 实现处理函数 -> 注册到MCP Server -> Agent自动发现。

### Agent自进化机制

> 这是Agent开发的前沿领域。核心思想是让Agent能够从自己的错误中学习，逐步改进自己的Prompt和策略。
>
> 基本实现：
> 1. 每次Agent执行失败时，记录失败场景和原因
> 2. 定期分析失败模式，提取“改进规则”
> 3. 将改进规则注入到Agent的System Prompt中
> 4. 验证改进效果，保留有效规则，回滚无效规则
>
> 这个领域目前仍处于早期阶段，但Google DeepMind 2025年的论文"Self-Improving Agents“已经展示了初步可行性——在特定任务上，自进化Agent在100轮迭代后性能提升了34%。
